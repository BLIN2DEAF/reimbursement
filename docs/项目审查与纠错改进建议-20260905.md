# 报销项目审查与纠错改进建议

审查日期：2026-09-05。依据当前工作目录中的源码（包含已有未提交修改）、现有测试和合成数据验证。此次未改动业务代码，未登录真实 BIP 或创建报销单。

## 判断

现有项目已经具备流程防错能力，下一阶段应优先解决数据正确性、人工纠错和失败恢复。建议先修复已确认的金额与编辑问题，再增加校验中心，最后补齐整单对账和断点恢复。

现有措施值得保留：识别异常拦截、多份审批单/补助单拦截、同会话重复操作锁、费用区身份及新增行检查、部分字段回读、发票批次金额核对、收款账号尾号回读，以及只保存草稿、不自动提交。模型调用也已有超时和最多两次 SDK 重试，不能笼统归为“没有重试”。

## 第一优先级：已确认的正确性问题

### 1. 文本补助单通过数字位置猜天数

位置：`src/document-parser.ts:690–698`。

文本解析会遍历全文数字，取第一个 2～30 的数字作为天数，找不到就设为 2；金额直接按配置费率计算。月份、日期、序号都可能被当作天数，票面实际金额未被可靠读取。

合成提取文本中包含 `Date: 2026-09-05`、`Trip days: 12` 时，实际得到 9 天；完全缺少有效天数时，得到 2 天、合计 360 元（测试标准为每日 100+80 元）。这验证的是现有文本处理分支，不是完整 PDF/OCR 链路。

建议：按字段标签、表头和行结构提取；缺失记为“待确认”，保留原文和页码。推算值只能作为有依据的建议值；未经核对不能替代实际识别结果。金额计算采用整数分。

### 2. 补助合计可能与真正填入 BIP 的明细不同

位置：`src/server.ts:327–348`；`src/bip-automation.ts:816–828`。

服务端把总额 0 当成缺失值自动补算，但部分分支只修改汇总、不修改明细；自动填单使用明细。已复现：3 天、1 人、伙食 300、交通 0，确认页交通合计变为 240，但自动填单读取的交通明细仍是 0。

另外，伙食总额不高于每日标准时，系统会按标准重写伙食和交通两项，可能覆盖真实扣减金额。合法的 0 元与识别失败不能混为一谈。

建议：使用一份权威明细，汇总只能由明细计算；区分“缺失”“确认为零”“识别值”“推算值”。推算与票面或扣减不一致时展示差异，要求修正或说明。不能静默改金额。

### 3. 人工修改的报销事由会在重绘时丢失

位置：`frontend/app.js:734–777`。

事由编辑只写页面元素，没有同步到数据；编辑补助时重新绘制确认页，旧事由覆盖新事由。已用实际编辑函数和模拟页面状态复现“先改事由，再改天数”的丢失。

建议：所有编辑先更新统一的数据模型，再渲染页面；立即保存修改，标记修改前后值，提供撤销。不要等到最终确认时才从页面收集事由。

## 第二优先级：补齐纠错闭环

### 4. 缺少完整的业务数据校验入口

位置：`src/server.ts:228–241`；`src/document-parser.ts:181–188`；`src/bip-automation.ts:3120–3141`。

确认消息可以直接替换服务端结果；运行前主要检查配置和事由。解析数值失败经常变成 0，日期格式提取也不等于真实日期有效性校验。未见统一检查发票关键字段、日期顺序、材料间人员/行程一致性和补助合计的入口。

建议在识别后、每次编辑后、启动填单前执行同一套服务端规则：

- 必须修正：缺少关键字段、无效日期、明细与合计不一致、文件不存在或不属于当前任务、明确重复材料。
- 需要核对：行程与审批日期不一致、住宿与审批范围不同、人员不一致、推算字段、多城市或多段住宿无法合并。
- 提示：非关键字段缺失、可解释的开票日期差异等。

日期应区分开票日期、出行日期、入住/离店日期；不能把全部日期都强制限制在审批期间。补助标准、扣减方式和例外按单位实际规则配置，不凭通用假设写死。

确认请求只接受允许修改的业务字段和版本号，服务端保留文件 ID 与路径映射并重算派生数据。确认页显示 `invoice_list`，上传使用 `invoices`，应通过稳定文件 ID 统一关联，避免未来“改了展示但没改填单数据”。

### 5. 可修改字段少，一个材料失败会阻塞整批

位置：`frontend/app.js:579–603`；`src/server.ts:262–270`。

目前主要能修改事由和补助。审批人员、目的地、日期、发票分类、住宿日期等缺少完整纠错入口。单个材料失败时整批无法进入确认；用户需要重新上传。

建议做“原件预览 + 字段编辑 + 问题说明”核对页：支持按文件重新识别、替换、排除、重分类，保留已正确识别的其他材料。每个字段能显示来源、原始值、人工改动及待确认状态。模型自报置信度只能参考，重点依靠来源证据和规则冲突。

另有一个明确分支遗漏：`isValidClassification` 允许“document / 其他凭证”，但 `processAllFiles` 没有接收普通凭证的分支，会进入错误列表（`src/document-parser.ts:751–761`）。建议普通凭证只做分类和附件归档，不要求解析成审批、补助或税表。

### 6. 缺少本地业务去重和任务恢复

位置：`src/file-processor.ts:74–81`；`src/server.ts:83–94、131–135`；`frontend/app.js:110–116`。

同名文件增加后缀保存，不等于去重。同会话锁也不能防止相同发票在新会话重复处理。前端刷新会新建会话，服务端状态只存内存；填单失败后没有继续原单的恢复入口。草稿已保存而影像失败时，整体仍呈现错误，重跑可能产生额外草稿。

建议：

- 文件内容摘要识别同文件重复；票据唯一编号及票据类型识别跨格式重复，号码缺失时只提示疑似重复。
- 本地保存任务 ID、材料清单、确认版本、已完成步骤、BIP 单号和最后核验结果。
- 分别显示“未保存”“草稿已保存、附件待完成”“完成”“结果待核实”。
- 恢复先读取原草稿状态；确认尚未执行后才重试增行、上传或保存，不能整段盲目重跑。
- 页面失联或结果不明时保留“待核实”，支持人工接管；不自动删除可能有效的草稿。

### 7. 最终成功缺少整单级证据

位置：`src/bip-automation.ts:2865–2903、3182–3190`。

目前已经有局部回读和发票批次金额检查。但“正在执行最终校验”之后立即返回报告，没有独立整单核验；附件保存主要依赖按钮点击、窗口关闭或没有可见错误，缺少重新读取已保存附件清单的正向证据。

建议生成确认版本的预期单据，填单后回读实际单据，逐项核对事由、分区金额、补助、账号、附件清单、单号和草稿状态。保存前检查当前页面，保存后检查持久化结果。只有关键项一致才显示“已完成核对”；取不到证据时显示“待核实”，不要等同于成功或直接重跑。

完成页展示：BIP 单号、预期/实际金额、材料数量、差异项和打开原单入口。账号完整可读时应完整匹配；只有掩码时，结合收款人和账户记录身份校验，尾号本身不能证明账户唯一。

## 第三优先级：材料覆盖与维护

### 8. 多页文件和复杂住宿需要明确支持边界

位置：`src/document-parser.ts:46、195–217`；`src/bip-automation.ts:2674–2676、2723–2725`。

扫描 PDF 仅识别首页，文本截取前 5000 字；一份文件固定产生一条分类与提取记录。后续页的人员、费用或票据可能遗漏。多张住宿票合并一条费用行时，入住信息仅来自首张票，多段或多城市可能失真。

建议：先检测页数，逐页识别并关联原件；明确一文件多票的拆分和上传策略，防止拆分后重复上传原件。住宿按实际城市、期间、人员分组；如果单位 BIP 流程要求只能合并一行，则先核对各票住宿信息是否兼容，不兼容就提示人工处理。

### 9. 单位规则和错误现场应更易维护

费用类型、人员级别等有多个固定值；自动化代码约 3200 行，将业务流程、页面定位、读写和诊断集中在一个类中。建议逐步拆成规则、页面操作、工作流和结果核验模块，规则带版本和适用范围。

会话超时当前只移除内存状态，没有对应材料保留/清理流程；部分错误截图和诊断文件使用公共文件名，会被后续任务覆盖。建议按任务归档并脱敏日志，提供用户可理解的材料保留期限和清理入口，保留未完成任务的恢复资料。

## 推荐落地次序与验收

1. **先修正确性问题**：移除猜天数和静默补算；统一明细/汇总；修复事由编辑丢失；接收普通凭证。验收：缺失天数不产生金额；确认的 0 元不被改写；页面合计等于填单明细；任意编辑顺序都保留修改。
2. **再加纠错中心**：服务端校验、逐字段编辑、单文件重试、原件来源、重复检查。验收：错误指出具体文件、字段和原因；修正一项只重算受影响部分；有未解决必改问题时不能启动填单。
3. **补齐完成核验与恢复**：保存任务及单号、关键步骤记录、整单回读、影像清单核对。验收：模拟断网、保存超时、附件失败和页面刷新后，能够确定现有单据状态并继续，且不重复建单或上传。
4. **扩展复杂材料**：多页多票、多城市住宿、多人和不同扣减规则。每种新增场景都有对应样例与验收标准。

优先增加针对错误场景的测试，而不是继续扩大正常流程测试数量：缺失/非法日期、真实零金额、扣减金额、重复票据、编辑持久性、前后端数据差异、保存结果不明和恢复不重复操作。
